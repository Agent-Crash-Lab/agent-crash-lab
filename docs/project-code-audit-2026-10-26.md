# 프로젝트 검증 및 시나리오·조사 연결 수정 — 2026-10-26

## 목적과 실행 구조

OOPS는 제조 운영 Agent에 예외 조건을 주고, 도구 호출·승인·DB 저장 결과를 대조해 QA 보고서를 만드는 플랫폼이다. 구매·생산·품질은 합성 참조 업무이며 실제 공장에 연결하지 않는다.

Frontend → Spring MCP 공개 API → Harness → Scenario Agent의 생성·두 관점 검토 → Harness의 데이터·정책·실행 계약 검사 → 대상 실행·코드 판정 → 필요 시 조사 Agent → 보고서 순서로 동작한다. 구매 상태는 Spring/PostgreSQL이, 생산·품질 상태는 Harness 시뮬레이터가 관리한다. Knowledge는 문헌 검색을 제공하며 업무 판정을 대신하지 않는다.

최신 `origin/main`의 `00bf03d`를 현재 `test`에 병합했다. 이 커밋의 파일 내용은 검증 기준 커밋 `261a370`과 같으며, 실행한 검증에 영향이 없다. 관련 원문은 [이슈 #29](https://github.com/Agent-Crash-Lab/agent-crash-lab/issues/29)다. README 수정과 기존 미추적 아키텍처 문서는 보존했다.

## 원인과 수정

| 경로 | 확인한 문제 | 수정·검증 |
|---|---|---|
| 생성 | 위험별 한 건을 요구하면서 근거 부족 시 제안을 생략하라는 안내가 공존했다. 빈 생성 결과도 기본 모델 스키마에서 허용했다. | 생략 대신 근거 한계를 검토에 전달하도록 안내를 통일하고, 생성 결과를 최소 한 건으로 제한했다. SDK의 요청별 정확한 개수 제한과 위험 범위 검사도 유지한다. |
| 근거 연결 | 이슈의 정책 인용 누락은 현재 브랜치의 서버 측 연결 코드로 일부 개선돼 있었다. | 모델의 인용 목록이 비어 있어도 검색된 연구·채택 정책이 연결되는 회귀를 추가했다. 제조업·Agentic 문헌과 채택 정책의 역할은 구분한다. |
| 부분 보완 | 실제 SDK 경로에서 일부 제안만 반환한 보완 결과를 원래 전체 위험 목록과 비교해 `DESIGN_RISK_COVERAGE_MISMATCH`로 거절했다. | 이번 보완 요청의 위험 목록과 비교한다. 나머지 제안과 ID·도구·위험 범위 보존을 검사한다. 수정 전 실패와 수정 후 통과를 확인했다. |
| 조사 시작 | Agent가 시작된 뒤 POST 응답만 유실돼도 조사 실패로 처리했다. | 같은 실행 ID를 조회해 요청의 종류·대상·입력이 일치하는 경우만 이어받는다. 시작 POST를 자동 재전송하지 않는다. |
| 조사 종료 | 구매 실행 완료 뒤 예상 밖 조사 예외가 나면 상위 예외 처리가 조사를 `RUNNING`으로 남겼다. | 실행 판정을 보존하고 조사 상태를 `ERROR`로 끝낸다. 외부 예외 원문은 공개 상태에 저장하지 않는다. |
| 오류 표시 | 조사 생략·실패·코드 요약을 상태 코드만으로 구분하기 어려웠다. | 생략 이유, 조사 중, 실패, 예산 소진, 보고서 근거 확인 필요, 코드 요약을 화면에서 구분한다. |
| 이벤트 | DB 저장 전에 버퍼 항목을 삭제해 저장 실패 시 이벤트가 사라지고 배경 저장 작업도 종료됐다. | 저장 성공 후 제거하고 DB 오류는 버퍼를 유지해 다음 주기에 재시도한다. 부분 저장·순서·중복 방지 회귀를 추가했다. |
| 서비스 경계 | 성공 HTTP 응답의 잘못된 JSON이 일반 예외로 빠졌다. 색인 테이블이 없을 때 검색은 내부 오류를 냈다. | 안전한 `ClientError`와 `KNOWLEDGE_NOT_INDEXED`로 변환한다. 검색 불가·위험 개수 불일치 코드는 UI까지 전달한다. |

FAIL 또는 INCONCLUSIVE가 없으면 조사 Agent를 호출하지 않는 기존 동작을 유지했다. 이는 조사 연결 실패와 다르다. 자료·업무 관계·실행 계약을 통과하지 못한 제안을 실행 가능으로 바꾸는 우회는 추가하지 않았다.

## 성능 개선

Agent의 승인 만료 확인은 0.2초마다 완료 이력을 포함한 모든 실행 JSON을 읽고 있었다. 기존 `one_active_run` 부분 인덱스와 같은 조건으로 활성 실행만 조회하도록 바꿨다. 복구·실행 중 여부 확인도 이 조회를 사용한다.

로컬 SQLite에서 완료 이력의 본문 크기를 약 2 KB로 두고, 크기별로 20회씩 5묶음을 측정한 중앙값이다. 실행이 없는 상태의 만료 확인 비용이며 전체 서비스 처리량 측정은 아니다.

| 완료 이력 | 변경 전, 1회 | 변경 후, 1회 |
|---:|---:|---:|
| 0건 | 0.0010 ms | 0.0010 ms |
| 1,000건 | 2.131 ms | 0.0013 ms |
| 5,000건 | 12.373 ms | 0.0011 ms |

## 실제 유료 LLM 및 서비스 연결

기존 환경과 다른 포트·임시 DB를 사용했다. 생성·구매 대상·조사는 `gpt-4o-mini-2024-07-18`, 두 관점 검토는 `gpt-5.4-mini-2026-03-17`을 호출했다. 생산·품질 대상 자체는 기존 규칙 기반 참조 구현이다. RAG·승인·MCP·DB·판정·조사는 실제 서비스를 사용했다.

| 설계 요청 | 제안 / 실행 가능 | 실제 실행 |
|---|---:|---|
| 구매, 최초 | 3 / 3 | RUN-001~004 |
| 구매, 최신 프롬프트 반복 | 3 / 3 | 생성·검토 재확인 |
| 생산 | 3 / 3 | RUN-005~008 |
| 품질 | 3 / 3 | RUN-009~012 |

각 유형의 B1 세 조건은 모두 완료됐고 FAIL·INCONCLUSIVE가 없었다. 각 유형의 B0 응답 유실 시험에서는 변경이 두 번 저장됐고, 구매는 FAIL 3개, 생산·품질은 각각 FAIL 2개로 판정했다. 세 실패 실행 모두 실제 조사 Agent가 완료돼 `validation.passed=true`인 보고서를 반환했다. 12개 실행의 최종 이벤트에 대해 수집 완료, 순번 연속성, ID 중복 없음, 조사 실행의 `REPORT_VALIDATED` 기록도 확인했다.

검토 수용과 실행 가능은 다른 결과다. 일부 LLM 검토는 `NEEDS_INFORMATION`이었으며 기존 탐색 실행 정책에 따라 근거 한계를 남긴 채 실행됐다. 이를 두 관점 검토의 전면 수용이나 안전성 증명으로 집계하지 않았다. 유료 보완은 이번 요청들에서 필요하지 않았고, 부분 보완 수정은 모델 대역 회귀로 검증했다.

별도 $0.20 상한 장부에서 총 33회 호출했고 사용량 기준 추정 비용은 **$0.1143825**, 미확정 예약 비용은 **$0**다. 기존 개발 환경의 비용 장부와 한도는 변경하지 않았다. 이는 모델 사용량을 저장소 요율로 계산한 추정이며 청구서 대사는 아니다.

원시 계획·실행·최종 이벤트·비용 장부는 Git 제외 경로 `artifacts/local-runs/code-audit/`에 보관했다. 실제 API 키와 기존 내부 토큰이 결과 JSON에 없는지도 확인했다. 프로젝트 전체 안전성이나 일반적인 LLM 생성 성공률을 입증하는 통계 실험은 아니다.
