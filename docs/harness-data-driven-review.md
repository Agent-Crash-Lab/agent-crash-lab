# Harness 공통화 점검

## 검토 결론

구매·생산·품질을 지금 바로 한 개의 범용 함수로 합치면 안 된다. **시험 생명주기와 증거 형식은 하나의 공통 Harness로 묶고, 업무 상태·도구·제약 판정은 데이터 설정과 업무별 Adapter로 분리하는 구조**가 적절하다.

세 업무는 승인·호출 기록·상태 초기화·결과 집계는 비슷하지만, 실제 업무 불변 조건과 저장소가 다르다.

- 구매는 MCP 도구와 PostgreSQL의 발주·승인·공급원 기록을 함께 관찰한다.
- 생산은 설비·선행 공정·시간 겹침 상태를 가상 시뮬레이터에서 검사한다.
- 품질은 검사 원자료·성적서·출하 상태를 검사한다.

그러므로 “코드는 공통이고 업무 데이터만 바뀐다”는 목표는 **공통 실행 경로에는 적용하되, 업무 판정 규칙까지 억지로 같은 규칙으로 만들지는 않는 것**으로 해석해야 한다.

## 현재 공통으로 쓰는 부분

- `planning.py`의 `QaPlanner`는 세 업무의 대상, 기능, 위험 템플릿을 읽어 기본 시험 계획을 만드는 공통 진입점이다.
- `build_designed()`는 Scenario Agent의 제안을 공통 계획에 연결하고 출처·리뷰·실행 지원 여부를 검사한다.
- `evaluation.py`는 시험 규칙별 결과를 합쳐 `PASS`, `FAIL`, `INCONCLUSIVE` 등을 계산한다.
- 각 Adapter는 `target`, `sample`, `capabilities`, `tests`, `rules_by_test`, `supports_sample`, `prepare_case` 같은 실행 정보를 제공한다.
- 생산과 품질은 `ManufacturingAdapter`와 같은 시뮬레이션·실행 경로를 사용한다.

## 업무별 코드 분기가 남아 있는 곳

| 위치 | 현재 분기 | 영향 |
|---|---|---|
| `runner.py` | SYSTEM 실행 시 구매는 MCP·DB oracle, 생산·품질은 `SimulationService`; 참조 구매 Agent 테스트는 별도 경로 | 업무 유형/시험 종류가 늘면 실행 분기 추가가 필요 |
| `simulation.py` | Agent에 노출할 조회 도구를 PRODUCTION·QUALITY별로 선택하고, 저장 전 제조 제약 검사를 수행 | 새 업무가 추가되면 MCP tool route와 관측 규칙을 수정해야 함 |
| `adapters/manufacturing.py` | 하나의 Adapter 안에서 `kind == PRODUCTION`과 그 외 QUALITY 규칙을 분기 | 두 업무의 일부 실행은 공유하지만 검증 로직은 조건문에 결합 |
| `generation.py` | 구매 공급원 검증과 생산/품질 업무 제약 확인을 유형별로 처리 | LLM 생성값 검증의 업무 로직이 한 함수 안에서 커짐 |
| `planning.py` | target 입력, 기능 구성, risk-to-test 매핑, base sample 저장에서 유형 분기 | 계획 생성과 업무별 정책 매핑이 섞임 |
| `reporting.py` | 시나리오 설명, 안전 기대 행동, 규칙 이름, 커버리지 판정이 유형·test ID에 의존 | 보고서가 데이터 기반이 아니라 일부 코드 표에 의존 |
| `catalog.py` | 테스트 ID·제목·Agent 종류를 별도 구매/생산/품질 상수로 구성 | 자료 파일과 코드 상수의 중복 관리 위험 |
| `oracle/` 및 `agent_checks.py` | 구매 전용 DB 관측·발주 규칙·참조 Agent 검사 | 구매의 트랜잭션 의미가 제조 시뮬레이터 추상화와 다름 |

## 권장 목표 구조

```text
Harness Core
  계획/검증 → 실행 수명주기 → 이벤트·증거 수집 → 공통 판정 형식 → 보고서 조립
       │
       ├── Purchase Adapter: 요청·공급원·승인·발주 DB 매핑 + 구매 제약 평가기
       ├── Production Adapter: 작업·설비·일정 매핑 + 생산 제약 평가기
       └── Quality Adapter: 로트·검사·성적서 매핑 + 품질 제약 평가기
```

### 설정 데이터에 둘 내용

- Agent 업무 이름·설명·도구 계약과 상태 Schema
- 위험/시나리오 ID, 제목, 기본 입력·상태 fixture
- 시나리오가 필요로 하는 Adapter capability
- 승인 조건, 주입 시점, fault 설정
- 보고서에 쓸 기대 행동·업무 용어·문구 템플릿
- 위험 ID에서 테스트 ID·필수 판정 규칙으로 가는 매핑

### 업무별 코드에 남길 내용

- DB에서 실제 발주·승인 증거를 읽는 쿼리
- 설비 일정 충돌, 선행 공정 순서, 검사 합격 같은 업무 의미 판정
- 도메인 상태를 도구 결과에 매핑하는 로직
- 기존 도구 런타임이나 저장소가 다른 경우의 연결 방식

이 구분을 두면 새 업무의 이름·fixture·문구·기본 위험 시나리오는 설정으로 추가할 수 있고, 새 업무 규칙이나 저장소 연결이 생길 때만 새 Adapter/Evaluator 코드를 작성한다. 규칙이 복잡한데 억지로 JSON 표현식으로만 바꾸면 검토하기 어렵고 취약해질 수 있으므로, 선언형 규칙과 코드 평가기 확장을 함께 둔다.

## 단계별 개선안

1. **공통 계약부터 고정:** 모든 Adapter가 초기화, 도구 목록/호출, 승인, fault, snapshot, condition check, evaluate를 같은 인터페이스로 제공하도록 정의한다.
2. **식별자·설명 표를 설정으로 이동:** test ID, 업무명, 기대 행동, 보고서 설명을 `qa/examples` 또는 별도 versioned manifest에서 관리한다. `reporting.py`의 업무별 문자열과 `catalog.py`의 중복 상수를 줄인다.
3. **판정 출력 정규화:** 업무별 Evaluator는 도메인 조건을 판단하되 결과는 공통 `check_id/rule_id/scope/verdict/reason/evidence_ids`로 반환한다. `evaluation.py`는 이 형식만 집계한다.
4. **생성 검증을 Adapter에 위임:** `generation.py`는 patch 적용·공통 Schema·승인/주입 순서만 검사하고, 공급원·설비·검사 상태의 구체 조건은 각 Adapter의 `validate_scenario()`에 위임한다.
5. **실행 분기 제거:** `runner.py`와 `simulation.py`가 adapter ID나 업무 유형을 직접 나열하지 않고, 등록된 Adapter의 실행 backend와 기능을 호출하도록 한다. 구매의 외부 MCP/DB backend와 생산·품질 simulator backend는 공통 인터페이스 뒤에서 계속 별도로 동작할 수 있다.
6. **업무별 골든 기록으로 회귀 확인:** 기존 구매·생산·품질 실행 기록의 입력, 도구 trace, 저장 결과, 판정을 새 경로와 비교한다. 결과가 달라지면 의도된 정책 변경인지 코드 회귀인지 구분한다.

## 피해야 할 단순화

- 업무별 규칙을 하나의 `if/else`에 계속 추가해 “공통 코드”라고 부르는 것
- 구매 DB의 승인·발주 의미를 생산/품질 상태 테이블에 억지로 맞추는 것
- `kind`만 바꾸면 모두 지원된다고 표시하는 것
- LLM 생성 데이터를 그대로 업무 판정에 쓰는 것
- 업무 규칙을 설명 불가능한 임의 JSON 규칙 언어로 전부 이동하는 것

실행 지원은 설정 이름만으로 선언하지 않고, 해당 Adapter·주입기·관측기·Evaluator가 실제 등록되어 있을 때만 `READY`여야 한다.

## 범위 판단

현재 코드는 이미 계획 생성과 평가 결과 형식을 일부 공유한다. 가장 큰 추가 중복은 **실행 backend와 보고서·시나리오 설명의 업무별 조건문, 생성 데이터 검증의 업무별 분기**에 있다. 먼저 Adapter 계약과 보고서 메타데이터를 정리하는 것이 전체 실행 코드를 한 번에 다시 쓰는 것보다 안전하고 효과적이다.

이 문서는 구조 검토와 목표안이다. 이번 검토에서는 실행 경로나 DB 스키마를 변경하지 않았다.
