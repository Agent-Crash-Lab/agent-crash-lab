# QA 화면

## 사용 순서

**평가 대상 → 시험 설계 → 실험 실행·승인 → 실행 분석 → 결과 비교**

1. `requester-01`로 로그인합니다. 비밀번호는 서버의 `DEMO_USER_PASSWORD` 설정입니다.
2. **평가 대상**에서 자재 구매·발주 / 생산 일정 / 품질·출하를 고릅니다. 세 유형 모두 참조 환경에서 실행할 수 있습니다.
3. **시험 설계**에서 Agent의 기능·근거·제안 시험을 확인합니다. 현재 기본은 규칙 기반이며 LLM 설계는 별도 설정입니다.
4. **실험 계획 실행**에서 시험·서버 정책·실행 한도를 골라 시작합니다. 정상 대조 시험도 함께 실행합니다.
5. 현재 실행을 열고 `approver-01`로 매번 승인 또는 거절합니다.
6. **실행 분석**에서 업무 변경 건수·판정·QA 보고서·조사 기록를 확인합니다. **결과 비교**는 같은 SYSTEM 시나리오의 완료된 실행 두 개를 사용합니다.

`COMPLETED`는 실행 종료입니다. 모든 검사가 통과했다는 뜻은 아닙니다.
생산·품질은 규칙 기반 참조 Agent와 시험용 MCP를 사용하며, 실제 설비를 조작하지 않습니다.
개별 구매·조사 Agent 점검과 직접 시나리오 설정은 개발용 펼침 메뉴에 둡니다.

## 실행·직접 확인

저장소 루트에서 기존 `.env`를 준비하고 실행합니다. `INTERNAL_API_TOKEN`은 비어 있으면 안 됩니다.

```sh
make dev-rag-up
```

화면: <http://127.0.0.1:5173/#agents>. 실제 주소는 `.env`의 `FRONTEND_PORT`를 따릅니다.
화면만 개발할 때는 `frontend/`에서 `npm run dev`를 사용합니다. Node 서버가 `/api`를 MCP 공개 API로 전달합니다.

## 주요 연결

| 위치 | 역할 |
|---|---|
| `dist/live.js`, `live-api.js` | 실제 QA 설계·실험·승인·분석 화면과 API 요청 |
| `dist/app.js` | 메뉴 전환과 데모 화면 |
| `dist/scene.js`, `topology.js`, `topologies.js` | 저장된 이벤트의 3D 흐름 표시 |
| `dist/registration.js`, `registry.js` | 데모 구조 등록·보관 |
| `nginx.conf`, `server.mjs` | 운영 컨테이너·개발 서버의 API 프록시 |

```text
브라우저 → MCP 인증 API → Harness → 설계·대상·조사 Agent
                                      → 실행 환경·DB 판정
```

로그인·승인은 MCP가 처리하며 사용자 식별 헤더는 서버에서 만듭니다. 내부 토큰은 브라우저에 입력하지 않습니다.
실행·계획·보고서는 서버에 저장하고, 로그인 토큰은 메모리에만 보관합니다. 새로고침 후 재로그인합니다.
화면은 JSON을 주기적으로 조회하고 최종 이벤트 수집까지 기다립니다. 모호한 실행 시작·승인 요청은 자동 재전송하지 않습니다.

## 비교와 데모

- B0/B1은 Agent 종류가 아니라 서버의 중복 방지 정책입니다. 같은 입력의 S03에서 B0 주문 2건 / B1 주문 1건을 비교합니다.
- 모델·프롬프트·데이터 등이 다르면 변경 조건도 확인합니다. 서버 방어 효과를 Agent 지능 향상으로 해석하지 않습니다.
- **데모 예시**는 내장 자료만 사용하는 별도 화면입니다. 실제 실행 기록과 섞지 않습니다.
- 3D 순번은 수집 순서입니다. 인과관계는 호출·승인·DB 근거를 함께 확인합니다.

## 검증

```sh
npm run check
npm test
```

테스트는 요청·상태 처리·데모 흐름·로컬 프록시를 검사합니다. 실제 API와 DB 연결은 통합 실행으로 별도 확인합니다.

[전체 구조](../docs/architecture.md) · [데이터](../docs/data-guide.md) · [평가 기준](../docs/evaluation.md)

S04 공급 자격 시험은 정상 대조와 해당 공급원의 승인 여부만 다릅니다. 실행 분석에서 Agent 행동과 실제 업무 상태를 따로 확인합니다. 같은 B1 서버에서 Agent 버전이 다른 두 S04 실행도 비교할 수 있습니다.


## 팀 공유 시 확인할 것

시험안의 검토 기록에서 기대 행동·문헌·상황의 일관성과 코드 사전 검사 이유를 펼쳐 봅니다. 수용 표시는 대상 Agent의 안전성 합격이 아닙니다. 실행 분석의 QA 보고서는 **대상 업무 → 위험 상황 → 기대 행동 → 관측/DB 변경 → 결과·한계** 순서입니다. 보고서와 최근 완료 시험 요약은 HTML로 저장할 수 있습니다.

기존 구매 중심 화면 캡처는 [실행](docs/screenshots/live-execution.jpg)·[조사](docs/screenshots/live-investigation-report.jpg)·[비교](docs/screenshots/live-comparison.jpg)에 보관합니다. 최신 세 유형 QA 화면과 완전히 같다는 뜻은 아닙니다.


## 후속 개발 연결 (2026-10-22)

공동 입력·출력·담당 경계는 [팀별 개발 계약](../docs/architecture.md#팀별-개발-계약), 저장 양식은 [데이터·스키마](../docs/data-guide.md#보완과-추가-실험-데이터)를 기준으로 맞춥니다. 시험안은 보류된 안만 1회 보완하며, 추가 실험은 원래 계획의 정상 대조·위험 조건을 기존 배치·승인 경로로 실행합니다.
